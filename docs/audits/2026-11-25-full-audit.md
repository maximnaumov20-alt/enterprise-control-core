## 1. Краткое заключение

ECC имеет работающую основу для учёта корпоративных IT-активов, программных лицензий, заявок обслуживания, сотрудников и подразделений. В репозитории присутствуют API, React/TypeScript frontend, PostgreSQL, миграции Alembic, Docker Compose, тесты, CI, security workflow и средства резервного копирования/восстановления.

При этом готовность к коммерческому внедрению не подтверждена. Ключевые незакрытые области: защита основной ветки, независимая оценка безопасности, завершение лицензирования и provenance-аудита зависимостей, frontend end-to-end тестирование, проверка эксплуатации и восстановления на отдельной инфраструктуре.

**Предварительная оценка готовности к коммерческому MVP: 40–45%.** Это экспертная ориентировочная оценка по результатам выборочного аудита, а не измеренный показатель и не гарантия безопасности.

## 4. Архитектура и API

**Наблюдения**
- Backend построен на FastAPI/Python.
- Frontend использует React и TypeScript.
- PostgreSQL используется как основная база данных.
- Миграции управляются Alembic.
- Docker Compose и CI используются для сборки и тестирования.

**Риски и рекомендации**
- Основная логика API сосредоточена в крупном `backend/app/main.py`. По мере роста системы рекомендуется разделять маршруты, схемы, сервисный слой и работу с хранилищем по доменам.
- Требуется отдельная матрица API-операций: endpoint, HTTP method, требуемая роль, tenant scope, валидация, audit event и негативные тесты.
- Выборочный просмотр API не является полным доказательством корректности всех маршрутов.

## 5. Аутентификация, авторизация и tenant isolation

В просмотренном коде обнаружены:
- JWT с алгоритмом HS256 и проверками issuer, audience и срока действия;
- хеширование паролей Argon2;
- проверка версии токена пользователя для инвалидирования старых токенов после изменений состояния учётной записи;
- ограничение попыток входа;
- роли admin/editor/viewer;
- проверки принадлежности объектов организации;
- tenant-scoped запросы и ограничения связей в базе данных.

В доступных тестах присутствуют проверки ролей, изоляции организаций и отказов доступа.

**Вывод:** в просмотренных участках не обнаружено очевидного обхода tenant isolation. Это ограниченный вывод по исходникам и тестам, а не заключение о безопасности всего API.

**Незавершённые задачи**
- MFA;
- полноценное управление сессиями и выборочный отзыв сессий;
- проверка восстановления пароля и безопасных сценариев смены учётных данных;
- независимый аудит JWT, RBAC и tenant isolation;
- проверка секретов, ротации ключей и конфигурации production.

## 6. Обработка ошибок и целостность данных

В просмотренных тестах и коде присутствуют обработка ошибок транзакций, откат при ошибках аудита и optimistic locking/version checks для ряда сущностей.

**Риск:** нельзя распространить эти выводы на все операции без полной проверки каждого маршрута и транзакционного сценария.

Рекомендуется добавить тесты конкурентных изменений, повторных запросов, конфликтов версий, частичных отказов и отката связанных операций для каждого домена.

## 7. Журнал аудита

Положительные признаки:
- аудит событий связан с бизнес-операциями;
- предусмотрен откат транзакции при ошибке записи аудита в проверенных сценариях;
- журнал ограничивается организацией;
- для ряда удаляемых сущностей сохраняются сведения о прежнем состоянии.

**Подтверждённое архитектурное ограничение:** обычная таблица аудита в той же базе не гарантирует неизменяемость записей от администратора БД или субъекта с достаточными правами.

Рекомендации:
1. ограничить права изменения/удаления audit rows;
2. вынести архивирование аудита в отдельный контур хранения;
3. рассмотреть hash chaining или подпись событий;
4. контролировать целостность и экспортировать записи в независимое хранилище;
5. описать срок хранения, доступ и процедуру расследования.

## 8. Миграции и база данных

В репозитории обнаружена последовательная цепочка Alembic от `0001_initial` до `0012_user_version`. CI содержит проверку миграций.

**Не проверено:** upgrade реальных старых установок на разных версиях, downgrade в поддерживаемых сценариях, поведение на больших объёмах, восстановление после прерывания миграции и совместимость с production-like данными.

Рекомендации:
- регулярно тестировать upgrade с каждой поддерживаемой базовой версии;
- тестировать восстановление перед миграцией;
- документировать backup/rollback процедуру;
- проверять ограничения и индексы на тестовых объёмах данных.

## 9. Frontend

**Риск:** успешная сборка не доказывает корректность пользовательских сценариев, доступности интерфейса, обработки ошибок API и поведения при смене ролей.

Рекомендации:
- unit-тесты для критичных компонентов и логики;
- e2e сценарии входа, управления активами, лицензиями, сотрудниками и заявками;
- проверки role-aware UI и отказа в доступе;
- тестирование пустых состояний, ошибок сети и истёкшей сессии.

## 10. Зависимости, SBOM и лицензии

Подтверждено наличие:
- `backend/requirements-runtime.in`;
- `backend/requirements-dev.in`;
- `backend/requirements-runtime.lock`;
- `backend/requirements-dev.lock`;
- `frontend/package.json`;
- `frontend/package-lock.json`.

Security workflow запускает pip-audit и npm audit, сканирует образы Trivy и формирует CycloneDX SBOM.

**Важное различие:** lock-файлы и успешный vulnerability scan не подтверждают совместимость лицензий, происхождение кода или право распространения компонентов.

В репозитории на момент проверки не обнаружен корневой LICENSE-файл. Лицензия ECC и правила коммерческого распространения остаются незавершёнными. Нужна юридическая проверка лицензий Python/npm пакетов, транзитивных зависимостей, системных пакетов контейнеров, шрифтов, иконок, изображений и скопированных фрагментов кода.

## 11. Docker, конфигурация и секреты

CI проверяет сборку Docker и Compose smoke test. В ходе ограниченного поиска по репозиторию не выявлены очевидные совпадения с несколькими типовыми форматами секретов.

**Ограничение:** это не полноценный secret scan. Нужны GitHub secret scanning/push protection или эквивалентный инструмент, сканирование истории Git, проверка runtime-конфигурации, ротация ключей и проверка прав контейнеров.

Необходимо отдельно подтвердить:
- отсутствие production secrets в образах и логах;
- безопасные значения по умолчанию;
- минимальные права контейнеров;
- TLS и сетевую сегментацию;
- процедуру ротации JWT и encryption keys;
- корректность health/readiness checks.

## 12. Резервное копирование и восстановление

В репозитории обнаружены backup/restore scripts, PostgreSQL archive validation, age encryption, S3 upload/read-back logic, SHA-256 checks, healthcheck, systemd service/timer и инструкции восстановления.

В CI присутствуют тесты backup/restore и архивных сценариев. В последних просмотренных workflow основной ветки соответствующие проверки прошли.

**Не подтверждено:** реальная интеграция с AWS/S3, IAM policies, фактическая долговечность хранения, восстановление ключей age, регулярное восстановление на отдельной среде, измеренные RPO/RTO и успешный disaster recovery drill в инфраструктуре заказчика.

Обязательные дальнейшие действия:
- настроить тестовый S3 bucket и отдельную IAM роль с минимальными правами;
- провести upload/read-back/restore drill;
- проверить процедуру хранения и восстановления ключей;
- измерить RPO/RTO;
- задокументировать retention и защиту от удаления/перезаписи;
- регулярно проверять systemd timer и оповещения о пропущенных резервных копиях.

## 14. Подтверждённые проблемы, риски и непроверенные области

### Подтверждённые проблемы
1. Branch protection для `main` не включён (`protected: false` на момент проверки).
2. Корневой LICENSE не обнаружен; выбор лицензии ECC не завершён.
3. Документация зависимостей содержала устаревшие сведения и ссылку на удалённый combined requirements файл. Исправление подготовлено в PR #122.
4. Frontend e2e/unit test suite не обнаружен в просмотренном дереве.

### Существенные риски
1. Нет независимого penetration test.
2. Журнал аудита не является криптографически неизменяемым хранилищем.
3. Production S3/DR процедура не подтверждена реальным испытанием.
4. Нет подтверждённого измерения RPO/RTO.
5. Большой backend entrypoint усложняет сопровождение и независимый review.
6. Автоматические сканы зависимостей не заменяют лицензионную проверку.

### Непроверенные области
- полный динамический тест каждого API endpoint;
- нагрузка, масштабирование и отказоустойчивость;
- реальная установка и обновление на чистом сервере;
- реальные S3 credentials/IAM и восстановление;
- полноценное восстановление из резервной копии после потери среды;
- ручная проверка секретов во всей Git history;
- юридическая проверка всех third-party assets и компонентов;
- независимая проверка безопасности.

## 18. Итог

ECC уже имеет существенную техническую основу и полезные эксплуатационные механизмы. Следующий этап должен быть сосредоточен не на бесконечном добавлении модулей, а на закрытии P1 рисков: защита основной ветки, лицензирование, MFA/session management, независимый аудит и защита журнала аудита. Затем необходимы полноценные frontend тесты и реальный DR drill.

**До закрытия этих пунктов ECC следует считать развивающейся системой для тестовой/пилотной среды, а не готовым к безусловному production-развёртыванию коммерческим продуктом.**
